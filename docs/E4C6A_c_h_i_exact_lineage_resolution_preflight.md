# E4C6A — C/H/I exact lineage resolution preflight

E4C6 intentionally used a broad lexical search and therefore produced hundreds of candidate matches, including self-matches and unrelated paths. That was acceptable for conservative discovery because it did not resolve C/H/I.

E4C6A narrows the search using historical phase identities fixed before this forensic.

The phase families are:

- C: `E3B4A`, `E3B4C3`, `E4C0`, `E4C2C`, `E4C2E`;
- H: `E4C3A`, `E4C3B`, `E4C3C`, `E4C3D`, `E4C3E`;
- I: `E4A2C`, `E4A2D`, `E4A2G`, `E4C4`.

These families were chosen from the pre-existing research chronology and E4C6 structural output, not from numerical economic results.

E4C6A freezes exact matching Git commits, tracked artifact paths, current SHA256 hashes, Git blob identities, and headers of result tables. It also inventories structural status lines from docs/metadata/scripts while suppressing lines containing non-integer decimal values.

No result-table numeric rows are read. No transform, estimator, representation, uncertainty method, component definition, or geometry rule is changed.

The purpose is to obtain enough exact lineage evidence to make a later explicit readiness decision for C, H, and I without contaminating that decision with broad lexical false positives.
